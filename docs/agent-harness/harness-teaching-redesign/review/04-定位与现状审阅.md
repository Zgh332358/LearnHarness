# 04｜定位与现状审阅

审阅日期：2026 年 10 月 7 日。对象：本会话新写的 本会话独立编写的全面指南，重点为第 11–13 章，并检查第 1–2 章定义及附录自测。审阅只读取这份新稿与官方技术资料；没有使用 learnDSH 或其原有源码、解释内容。本文件不修改主稿。

**结论：现稿的定位骨架可以保留。** 它已经分别回答“承担什么运行职责”“实际在哪里运行”“开发者拿到多少现成机制”，没有把逻辑图误当部署图，也没有将 SDK、框架、运行时和 Harness 排成统一的成熟度等级。当前产品事实总体有来源、有日期、有接入边界。正式定稿需要小幅补足名称边界和 Codex 可复用运行系统，并给定位目标增加一道可检查的读者任务。

现稿中几处容易出错的事实已经处理得准确：Claude Agent SDK 使用开发者管理的进程和 Claude Code 二进制程序；Managed Agents 核查日仍标为 Beta，并可采用自托管执行环境；Responses 可参与托管工具与服务端能力，不能绝对归为纯文本模型接口；Deep Agents 的规划清单不应当作所有 Harness 的必需部分。核查依据分别是 [Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)、[Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview)、[OpenAI Agents 方案对照](https://developers.openai.com/api/docs/guides/agents)、[Deep Agents 概览](https://docs.langchain.com/oss/python/deepagents/overview)。这些是核查日文档事实，不证明所有账户都已经开通。

## 定稿前建议

### 1．名称分类还需要再退后一步：按责任比较，避免记厂商标签

位置：第 13 章 LangGraph 与 Deep Agents 段，原稿约第 908 行。

现稿准确说明 [LangChain 分类](https://docs.langchain.com/oss/python/concepts/products) 将 OpenAI Agents SDK 放在 framework 一栏，也提醒不是统一标准。但非技术读者仍可能把这张分类记成“OpenAI SDK 是框架，所以不是 Harness”。OpenAI 自己的 [Agents SDK 官方示例说明](https://developers.openai.com/cookbook/examples/agents_sdk/migrate-from-claude-agent-sdk/readme) 使用了 “model-native harness” 一词。这两种命名口径说明标签有重叠，不能证明某个产品具有或缺少一套固定功能。

建议将现有分类段缩为名称边界说明，正文继续以“谁组织循环、提供哪些输入与状态机制、谁部署、谁控制业务权限”解释。无需增加迁移教程或 SDK 配置细节。现有职责表可以保留，表述按能力而非厂商类别决定。

### 2．补一小段可复用 Codex Harness，避免把 Codex 只理解成托管 API 的内部名字

位置：第 13 章 OpenAI 段及职责表，原稿约第 895–923 行。

当前官方 [Codex 平台说明](https://developers.openai.com/blog/codex-as-a-platform)（2026 年 8 月 19 日）说明可通过 Codex SDK 或 app-server 使用已有 Codex 运行机制；开放运行与接入层、模型访问、托管服务需要区分。现稿仅在 Agents API 的托管 Harness 中提及 Codex，覆盖略偏向托管路线。

建议只补一段定位和必要时一行职责对照：开发者接入已有 Codex 运行系统，应用仍负责业务上下文、工具和控制。它用于说明“复用已有 Harness”与“服务商托管运行”不同，不展开安装、调用代码或产品排名。独立可合并短文已放在 `work/position-addendum.md`。

### 3．架构图给少量关键箭头加具体内容

位置：第 12 章逻辑图与部署图，原稿约第 797–847 行。

技术关系没有明显错误，但部署图的双向箭头没有说明往返内容。目标用户已经接受输入、输出、执行；正式 HTML 应让他看见“模型输入／模型输出”“动作请求／业务返回”“保存／读取”等文字，而不用猜箭头含义。控制条件不要与资料传递共用同一种未标记线。

这是依据教材方法 [D01 固定对象与因果方向](../references/display/D01-fixed-objects-causal-direction.md) 作出的设计建议，不是产品事实或原站效果结论。先给一种部署完整路径，再显示只移动循环所在地点的对照；不在同一图里同时堆全部产品与全部环境。

### 4．补一道直接检验“定位”的题，而不是继续增加术语

现稿附录 B 的十题覆盖执行事实、恢复、评分和成本，但没有直接要求读者判断部署位置与接入责任。需求基线的“定位”和“当前产品”验收因此还缺少明确的检查任务。

建议复用餐厅例：界面在用户电脑，Harness 在托管服务，查询工具在业务方服务器，模型由模型服务计算。让读者指出谁组织后续输入、谁取得餐厅数据、谁定义未经同意不能预订；再只把 Harness 移到自有服务器，判断哪些职责会随部署改变。答案应引用图中对象与业务条件，说明地点变化并不自动赋予工具权限。

这种固定输入、只改变一项的比较依据 [D03 最小差异对照](../references/display/D03-same-input-minimal-difference.md)，先选再揭示依据可参考 [I03 判断与反馈](../references/interaction/I03-先作预测再看依据反馈.md)。这是作者迁移方案；尚未证明目标读者完成题目就已普遍掌握 Harness。

## 当前发展说明的边界

第 13 章选出的长任务、环境反馈、结构调整、托管恢复和动态工作流节点，能够解释工程关注点怎样拓宽。它们不构成行业统一阶段，现稿已明确这一点，建议维持。Programmatic Tool Calling 段已经区分模型生成协调程序、受限运行时执行程序、应用执行自有函数工具；同样应保留，不能退回“一次 API 返回只有一次模型判断”或“所有工具都是客户端执行”的绝对说法。[官方 Programmatic Tool Calling](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)

不需要补充排行榜、总体采用率、所有框架清单、模型内部思考或无来源的诞生年表。当前版本与 Beta 描述应继续附核查日期；文档提供接入资料，不等于本项目完成了真实账户开通或端到端产品测试。

## 方法研究与技术核查分别证明什么

100 轮方法研究是本项目对展现、交互和迁移风险的设计记录；其完成状态由项目总记录管理。本次审阅读取相关方法文件，用于判断图、对照与自测怎样组织，不将轮数或案例受欢迎程度作为理解效果证据。

技术定位与产品职责取自以上官方文档及工程文章。它们支持事实和有限工程归纳；教学例、三条定位轴、表格分类与读者任务属于本文组织。两套来源应分别保留链接：方法资料不能替产品功能背书，产品官方说明也不能证明非技术读者已经理解教材。浏览器操作验证、真实产品接入验证、目标读者测试还应分别报告，不能互相替代。

完成上述小改后，可以进入定稿与 HTML 实施；本审阅没有要求推倒前面已有技术主线。
