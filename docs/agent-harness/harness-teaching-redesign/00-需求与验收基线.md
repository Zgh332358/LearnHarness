# Harness 教程优化：需求与验收基线

版本：1.0。建立日期：2026 年 10 月 7 日。依据：本次会话中用户的明确要求与纠正。

## 目标受众

读者没有软件开发背景，但愿意理解技术逻辑。读者认可“输入、输出、执行”等准确的技术用语；不应把非技术背景理解为只能接受类比或去掉技术细节。文字应先给具体对象、过程与数据，再解释术语。

## 要解决的学习问题

读者读完需要知道 Harness 怎样让模型参与持续工作，以及它在系统架构、部署和当前产品中的位置。教程必须完整，同时应能沿一条主线理解；章节数量或字数本身不是学习效果证据。

核心过程是：目标与约束 → 本轮输入 → 模型输出 → 请求识别与条件检查 → 实际执行 → 返回与记录 → 后续输入 → 继续、等待、恢复或结束 → 结果验收。

读者应能回答：谁提出动作，谁真正执行，结果取得了什么，哪些事实仍未知，下一轮依据什么判断，系统为什么停止或继续。系统位置、实际运行地点、SDK/框架/托管服务的责任需要分别说明。

## 内容范围

1. 模型、Harness、工具、Agent 产品的职责。
2. 一轮与多轮调用：真实数据单、请求/结果编号、输出分支与反馈。
3. 工具说明与实现、参数结构、业务含义、授权、失败、重试与副作用。
4. 上下文、容量、选择、检索、压缩，与外部状态和记忆的分工。
5. 长任务的进度保存、中断恢复、外部状态核对。
6. 计划、工作流、并行与多 Agent 的适用条件和交接。
7. MCP、Skill、SDK、Framework、Runtime 的位置。
8. Harness 的逻辑位置、物理部署和当前技术发展。
9. 任务验证、系统评测、追踪、费用、延迟与真实项目阅读。

## 图文与交互要求

图解应展示具体关系：数据传给谁，状态怎样改变，控制条件触发哪个分支。用户已明确指出先前强行使用 3D 不直观、不本质。采用二维表达；空间效果不作为技术深度的代替。

交互应让读者观察机制：做一个选择、查看变化、得到解释。优先保留少量能解释关键因果的交互。不能仅添加按钮、动画、视觉装饰或术语卡片来称为图文教材。

保留完整深度，但用正文主线、就近图解、按需展开的协议细节和具体反馈组织阅读。不能把内容缩成几个概念摘要；也不应把所有步骤和设置同时堆给读者。

## 研究与循环要求

先建立本基线，再研究优秀 HTML 电子教材。研究以“展现方法”和“交互方法”为单位，记录一手案例、观察依据、适用条件、迁移方案和风险，存放独立方法文件夹。

执行 100 次有记录的研究—对照—判断循环。每次应包含一个实际问题、可追溯的观察、对当前需求的判断、明确决策与下一步。工具调用次数不等于循环次数；不能用同一条观察复制成 100 条完成记录。循环完成后，才进行现有教程大纲与逻辑审阅、技术/产品补足和正式定稿；定稿后实施 HTML 与内容调整。

## 验收任务

| 要判断的能力 | 读者任务 | 通过标准 |
| --- | --- | --- |
| 基本运行 | 追踪查甲已满后查乙的两轮 | 能区分请求、执行、结果、新输入，并指出每方责任 |
| 结果与证据 | 比较执行成功、业务不满足、结果未知 | 保留三种区别，不把无结果写成明确事实 |
| 连续工作 | 压缩输入后继续，或中断后恢复 | 能说明外部记录如何被取回，恢复前为什么核对已发操作 |
| 控制与验收 | 修改条件、暂停审批、取消或结束 | 能指出规则、授权、状态和验收分别在哪一步起作用 |
| 定位 | 比较本机、应用服务器和托管 Harness | 能区分运行职责与部署位置，指出接入者仍负责什么 |
| 当前产品 | 阅读 API/SDK/框架/托管方案对照 | 按实际责任判断，而不按名称推断统一层级 |
| 易读性 | 使用目录、图、交互与自测完成以上任务 | 主线清楚，图文对应；交互有反馈，可用键盘和窄屏阅读 |

这是教材设计验收与代理走查标准。没有真实目标用户参加时，不声称已经证明非技术读者普遍能理解；以任务模拟、独立审阅与浏览器验证报告其覆盖范围。

## 来源与边界

技术与产品事实使用联网一手资料并注明核查日期。教材方法研究从原作者、教材发布方和真实页面取得证据；说明哪些只是页面文本观察，哪些已经操作验证。

新通用教程不参考 learnDSH 的原有 DeepSeek 源码或旧解释内容。后续审阅只针对本会话新写的 Harness 指南与阅读版。保持既有原始资料作为独立资料，不用它们为新稿背书。
