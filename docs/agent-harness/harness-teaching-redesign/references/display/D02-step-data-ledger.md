# D02｜步骤数据表与稳定编号

方法类型：展现（display）。综合日期：2026 年 10 月 7 日。

本文根据 16 个案例的研究记录提炼展现规格，不是现有教程大纲审阅或 HTML 实现。来源部分是已有页面观察；下面的迁移方案、排版与检查均为基于需求基线的设计推断，尚未经过目标读者实验。部分源观察属于交互，但本文只提炼它们需要怎样显示对象、数据与解释。

## 目标问题

读者看到“查询→反馈→再思考”后，是否仍不知道具体查询了什么、执行到哪里、返回为空还是未知、下一轮使用哪条结果？动词图需要可以逐项核对的数据。

## 排版与图的具体结构

1. 在流程图附近放当前事件的数据单。建议固定字段为事件编号、负责方、输入／发送内容、发生的动作、返回内容、执行状态、业务含义；编号贯穿后续引用。

2. 把“提出请求”“识别与检查请求”“真正执行”“收到返回”记为不同可观察事件，或至少给同一请求的明确阶段列。请求编号和结果编号可配对，但不预先填入尚未发生的结果。

3. 当前状态与累计记录分别呈现。主面板只显示截至该步已取得的信息；历史区可查此前事件，后续结果不能提前出现在前一轮输入。

4. 重要状态用文字区分：未执行、执行失败、执行成功、业务不满足、事实仍未知。不要把执行成功直接写成任务成功。

5. 方案中的依据引用结果编号；选择编号时可找到原始返回和本轮纳入的字段。数据单解释公开输入与事件，不能编造模型不可见的内部思考。

## Harness 中适用与不适用的地方

**适用：** 适合两轮失败转查、工具参数和返回、上下文组装、恢复前核对已发操作、日志与最终方案的来源关系。它帮助非技术读者从具体数据理解请求与执行。

**不适用：** 不适合把完整原始日志不加选择地铺满正文，也不能把日志表当真实业务事实已经成立的证明。费用字段需要有计算或来源，不随示意步骤编造测量结果。

## 手机与静态回退

**手机：** 将每个事件行转成带字段标签的纵向数据单，始终露出编号与状态。原始长字符串独立展开；不能靠横向滑动才能看到状态与业务含义。

**静态回退：** 保留三到五个有区别的关键事件与完整字段，另附累计事件表。阅读顺序用编号表达，读者无需操作高亮即可追踪请求与结果。

## 使用本方法时的检查

- 读者能配对某请求、其执行状态和返回。
- 在一个早期步骤的数据单中，找不到未来才出现的证据。
- 同一事实在最终方案、返回表、后续输入中使用一致编号。

这些检查是未来教材与实现的验收要求，不是已经通过的测试。
