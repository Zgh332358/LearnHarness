# I07 失败与停止分支的可见反馈

方法状态：候选综合，2026 年 10 月 7 日。归纳依据均为 text；下表是 Harness 教学迁移判断，不是来源案例的技术结论或实际工具记录。

## 目标问题

读者能否把“条件拒绝、执行失败、业务不满足、结果未知、达到上限”分别定位，并根据证据选择继续、等待、核对或结束？它们不能被一个红色失败标签或绿色成功标签覆盖。

## 最小控件

一个情境选择器，三个或四个后续动作选项，“显示依据”按钮。默认只有一个情境，避免全套错误设置同时出现。每次选择展示触发阶段、规则、记录变化和仍未知的事实。

## 前 → 操作 → 后

| 前 | 操作 | 后与应显示的解释 |
| --- | --- | --- |
| 拟执行需要授权的动作，授权缺失 | 选择后续动作 | 条件检查不允许执行，进入等待；不能记录为已经提交 |
| 只读查询明确返回错误，有替代工具且允许使用 | 选择替代查询 | 保留错误与进度，形成下一次请求；重试次数仍受限制 |
| 查询有响应，但给出的套餐不符合忌口 | 选择替换候选或补查 | 执行结果保留，业务判断不满足；不把传输成功改成餐厅适合 |
| 提交预订后超时，订单是否生成未知 | 选择查询订单状态 | 先核对外部状态，再判断是否重试；未知不能改写成明确失败 |
| 运行达到本例上限，仍缺关键信息 | 选择结束 | 交付部分结果与缺项，说明停止理由；上限达到不等于任务完成 |
| 用户取消后续工作 | 选择停止 | 后续动作不再继续，记录已经发生的动作；取消不能自动撤销外部结果 |

这些动作只在明确给出的教学工具、授权与规则中判断。现实系统可能有专门的去重键、事务或审批机制，需按具体资料解释，不能用一道模拟题替代全部实现。

## Harness 迁移条件

必须区分动作提出、允许执行、已提交、已有响应与业务验收这些时点。工具返回字段依实际定义解释，不把通用 success 标签当成统一业务含义。停止与恢复均使用外部记录作依据；持久记录本身不能证明动作已完成。

## 禁止的误导

不对所有错误无条件重试；不把超时解释成订单不存在；不把用户取消解释成撤销已执行动作；不让教学条件限制冒充真实账号权限；不使用动画结束或进度满格代替验收。现实风险不能伪造为确定数值。

## 键盘与手机要求

选择器与动作可用键盘，不要求点击图中狭小分支；情境反馈有文字标题、字段和值，不只改变颜色。手机按“已知事实→可选动作→依据→新状态”顺序展示。选择变更后保留焦点，明确哪些记录新增、哪些保持不变。

## 证据边界与后续验证

来源均为 text，未操作原站。后续逐一核查拒绝时没有写入执行记录、未知状态未被覆写、上限与业务完成分开、取消后不继续，以及所有反馈选项都有准确理由。尚未真实目标读者测试。
